# Database Schema

This document describes the SQLite schema backing the `tracker` Django app.
The database file lives at `tracker/db.sqlite3` (created by `tracker/setup.py`).

There are three application tables — `Task`, `TaskTemplate`, `AuditLog` — plus
the standard Django bookkeeping tables (`django_migrations`, `django_session`,
etc.) created by the framework.

---

## Table: `tracker_task`

Concrete tasks scheduled for a particular day. One row per assigned,
scheduled piece of work.

| Field             | Type           | Notes                                                                                  |
|-------------------|----------------|----------------------------------------------------------------------------------------|
| `id`              | integer        | Primary key, auto-increment.                                                           |
| `task_name`       | varchar(255)   | Display name. Required.                                                                |
| `assigned_to`     | varchar(255)   | Free-form assignee name. Required.                                                     |
| `sla_days`        | integer        | Number of SLA days. Required.                                                          |
| `sla_type`        | varchar(20)    | One of `Working Day` or `Calendar Day` (see choices below). Required.                  |
| `scheduled_date`  | date           | When the task is due to start. Required.                                               |
| `finished`        | boolean        | `false` by default.                                                                    |
| `completion_date` | date (nullable)| Set when the task is finished. May be blank.                                           |
| `comments`        | text           | Free-form notes. Blank by default.                                                     |
| `month`           | date           | Used to group tasks into a month bucket. Required.                                     |
| `created_at`      | datetime       | Set automatically on row creation (`auto_now_add`).                                    |
| `updated_at`      | datetime       | Set automatically on every save (`auto_now`).                                          |

**Choices for `sla_type`:**

| Value           | Label          |
|-----------------|----------------|
| `Working Day`   | Working Day    |
| `Calendar Day`  | Calendar Day   |

**Default ordering:** `scheduled_date` ascending, then `task_name` ascending.

**String representation:** `task_name`.

## Table: `tracker_tasktemplate`

Reusable task blueprints. A new `Task` row can be generated from a template
for a given month; the template itself is not tied to a date.

| Field         | Type         | Notes                                                                 |
|---------------|--------------|-----------------------------------------------------------------------|
| `id`          | integer      | Primary key, auto-increment.                                          |
| `task_name`   | varchar(255) | Display name. Required.                                               |
| `assigned_to` | varchar(255) | Free-form assignee name. Required.                                    |
| `sla_days`    | integer      | Number of SLA days. Required.                                         |
| `sla_type`    | varchar(20)  | One of `Working Day` or `Calendar Day` (same choices as `Task`).       |
| `sort_order`  | integer      | Controls display order. Default `0`.                                  |

**Choices for `sla_type`:** identical to `Task` (see above).

**Default ordering:** `sort_order` ascending, then `task_name` ascending.

**String representation:** `task_name`.

---

## Table: `tracker_auditlog`

Append-only history of changes made to `Task` rows. One row per recorded
action.

| Field       | Type           | Notes                                                                                              |
|-------------|----------------|----------------------------------------------------------------------------------------------------|
| `id`        | integer        | Primary key, auto-increment.                                                                       |
| `task_id`   | integer (FK)   | FK to `tracker_task.id`. `on_delete=SET_NULL`, nullable — the log row survives task deletion.       |
| `task_name` | varchar(255)   | Snapshot of the task name at the time of the action. Required.                                     |
| `action`    | varchar(50)    | One of `created`, `updated`, `deleted` (used by `readable_message`).                               |
| `changes`   | json (default `{}`) | For `updated` rows, a dict with `{"old": {...}, "new": {...}}` showing the field-level diff.  |
| `timestamp` | datetime       | Set automatically on row creation (`auto_now_add`).                                                |

**Default ordering:** `timestamp` descending (most recent first).

**`readable_message()`** renders a human-readable line:

- `created` → `Created task '<task_name>'`
- `deleted` → `Deleted task '<task_name>'`
- `updated` → either a per-field diff list (e.g. `modified Assigned To from 'A' to 'B', modified Finished from 'False' to 'True' at 2026-07-10 09:30`) or, if `old`/`new` keys are missing, a generic `Updated task '<task_name>'`.
- otherwise → `<action> - <task_name>`

**String representation:** `readable_message()`.

## Relationships

```
tracker_tasktemplate   (no FKs; standalone)
        │
        │ (template → task generation happens in views, not enforced by FK)
        ▼
tracker_task ◄──── tracker_auditlog.task (FK, SET_NULL on delete)
```

- `AuditLog → Task` is a nullable FK with `on_delete=SET_NULL`, so deleting a
  `Task` keeps its history (the log row's `task_id` becomes NULL while
  `task_name` retains the snapshot).
- `TaskTemplate` has no foreign keys; it is a pure configuration row.

---

## Notes

- All three tables are managed by Django migrations under `tracker/migrations/`.
- The schema is SQLite-specific in practice (default `DATABASES` config), but
  the column types above are Django's portable representations and would map
  cleanly to PostgreSQL or MySQL if the engine is changed.
- Indexes: only the implicit primary-key indexes are created. There are no
  explicit `db_index=True` fields or `Meta.indexes` defined.
